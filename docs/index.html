A list that learns what you look up most

A self-organizing data structure written in C. It watches how keys are accessed, reorders itself to make popular keys cheap to find, and measures whether the change was worth the cost.

Observe, adapt, measure, prove

Real workloads don’t stay still: popular keys change, bursts come and go. A fixed structure stays correct but can become slow. This project tests whether light-weight adaptation reduces work, and makes the trade-offs visible.

Observe

Count hits per key in a sliding window of 1,024 lookups.

Adapt

Classify the traffic as uniform, skewed or shifting, then pick a policy.

Measure

Count comparisons, reorder steps, time, memory and policy switches.

Prove

Replay identical seeded traces on every structure and publish the CSVs.

Policies

  • Fixed list: the baseline. Never reorders.
  • Move-to-Front: a found key jumps to the head.
  • Transpose: a found key swaps one step forward.
  • Frequency Count: keeps the list sorted by hit count.
  • Adaptive: turns Move-to-Front on only when the window looks skewed.

Built to be extended

  • Strategy: policies are swappable function pointers.
  • Observer: access and policy-change events can be hooked.
  • Factory and Adapter: one get / put / erase API over every backend.
  • Command: workload operations are replayable objects.

What the benchmark shows

1,000 keys, 100,000 lookups, seed 42. Each bar is the average number of comparisons per successful lookup: shorter is better. These counts are deterministic, so you get the same numbers on any machine.

  • On skewed traffic, self-organizing lists do roughly four to five times less lookup work than the fixed list.
  • On a sequential scan, plain Move-to-Front does about twice the work of the fixed list. The adaptive policy notices the low skew and avoids that penalty.
  • On uniform traffic nothing helps, and the small differences are noise.
  • Adaptive pays a small price against always-Move-to-Front on skewed traffic (its warm-up window and monitoring), and in return it never collapses on a scan.
  • After the hot set changes, Move-to-Front and adaptive recover within 250 accesses. Frequency Count and Transpose need about 10,000, because old counts and slow one-step moves take time to overcome.

One list size and one seed. Run it with your own --n and --seed before drawing conclusions. Adaptive can win on one workload and lose on another.

Run it yourself

Pure C11 with no dependencies other than the math library.

git clone https://github.com/asutosh-source/self-organizing-ds.git
cd self-organizing-ds
make          # build
make test     # 24 checks against a reference model
make demo     # watch lists reorder and the policy switch
make bench    # writes results.csv and timeline.csv

Every benchmark lookup is also verified against the stored value, so a speed-up can’t come from a wrong answer.
